# LLM 비교 실험

SmartDoc AI의 답변 품질이 **모델과 방식(일반 RAG / Agent)에 따라 얼마나 달라지는지** 같은 조건에서 측정하는 실험입니다.

## 실험 설계

공정한 비교를 위해 **검색 단계는 모두 고정**하고, 답변을 만드는 LLM만 바꿉니다.

| 고정 | 바꾸는 것 |
|---|---|
| 문서, 청크 크기(800/100), 임베딩(`nomic-embed-text`), Chroma, top-k(4), 프롬프트 | 답변 LLM, RAG 방식(rag / agent) |

`rag_chain.ask()`와 `agent_graph.ask_agent()`에 `llm` 인자를 추가해, 기존 서비스 코드는 그대로 두고 모델만 주입할 수 있게 했습니다. 인자를 넘기지 않으면 기존처럼 로컬 Ollama 모델을 사용합니다.

## 평가 데이터셋 (`dataset.jsonl`)

포트폴리오 PDF를 대상 문서로 쓰는 질문 26개입니다.

- **답변 가능 18개**: 문서에 정답이 있는 질문. 정답 키워드(대체 표현 포함)를 모두 담아야 정답
- **답변 불가 8개**: 문서에 없는 정보를 묻는 질문. 지어내지 않고 모른다고 해야 정답

다른 문서로 실험하려면 같은 형식으로 질문을 새로 만들면 됩니다.

```json
{"id": "A01", "question": "...", "answerable": true, "keywords": [["chroma", "크로마"]]}
{"id": "U01", "question": "...", "answerable": false}
```

## 측정 지표

| 지표 | 의미 |
|---|---|
| 정답률 | 답변 가능 질문 중 정답 키워드를 모두 포함한 비율 |
| 거절 정확도 | 답변 불가 질문에 모른다고 답한 비율 (못 하면 환각) |
| 검색 실패 / 생성 실패 | 정답 근거가 검색 결과에 없었는지, 있었는데 답이 틀렸는지 구분 |
| 잘못된 거절 | 근거가 있는데도 모른다고 답한 경우 |
| 외국 문자 혼입 | 한국어 답변에 일본어·한자가 섞인 경우 (작은 모델에서 실제로 관찰된 문제) |
| 응답 시간 | 평균, p90 (첫 호출의 모델 로딩 시간은 제외) |
| 토큰 / 비용 | 질문당 평균 입력·출력 토큰, 100문항당 예상 비용 |

## 실행 방법

```powershell
# 1) 추가 패키지 (쓸 provider만)
pip install -r requirements-eval.txt

# 2) API 키 설정 (PowerShell, 현재 창에서만 유효)
$env:OPENAI_API_KEY = "sk-..."
# $env:ANTHROPIC_API_KEY = "..."
# $env:GOOGLE_API_KEY = "..."

# 3) 빠른 확인: 질문 3개만
python -m eval.run_eval --doc "data/uploads/박성주_AI_Engineer_포트폴리오.pdf" --models ollama:qwen2.5:3b --modes rag --limit 3

# 4) 본 실험
python -m eval.run_eval --doc "data/uploads/박성주_AI_Engineer_포트폴리오.pdf" `
  --models ollama:qwen2.5:3b openai:gpt-4o-mini --modes rag agent
```

프로젝트 루트(`smartdoc-ai/`)에서 실행합니다. 결과는 `eval/results/<날짜_시간>/`에 저장됩니다.

- `summary.md`: 모델·방식별 요약 표
- `results.csv`: 질문별 상세 결과 (엑셀로 열 수 있음)
- `failures.md`: 틀린 질문의 답변과 실패 원인

비용을 계산하려면 `models.py`의 `PRICE_PER_1M_TOKENS`에 각 회사 공식 가격표의 값을 넣으세요.

## 결과

### 실험 환경
- 문서: 포트폴리오 PDF 1개 (7개 청크), 검색 top-k 4
- 로컬 모델: Ollama `qwen2.5:3b` (Intel i7-1355U, GPU 없음, 16GB RAM)
- API 모델: `gemini-3.5-flash-lite` (Google AI Studio 무료 등급)
- 각 조합 1회 실행. 응답 시간은 무료 등급 한도를 지키려고 기다린 시간을 뺀 값

### 결과 요약

| 모델 | 방식 | 정답률 (18문항) | 거절 정확도 (8문항) | 재검색 횟수 | 평균 응답(초) | 평균 입력 토큰 |
|---|---|---|---|---|---|---|
| qwen2.5:3b | RAG | 72% | 100% | - | 17.0 | 1,379 |
| qwen2.5:3b | Agent | 83% | 100% | 50 | 76.0 | 5,664 |
| gemini-3.5-flash-lite | RAG | 100% | 100% | - | 4.7 | 1,201 |
| gemini-3.5-flash-lite | Agent | 100% | 100% | 18 | 4.5 | 3,243 |

### 발견한 점

**1. 틀린 원인은 모두 '생성 단계'였다**
검색 실패는 모든 조합에서 0건이었습니다. qwen이 틀린 문제는 모두 정답 근거를 검색해 왔는데도 답을 잘못 만든 경우였습니다.
- 기술 태그로만 적힌 "Ollama (Qwen2.5)"를 "로컬 LLM 모델" 질문과 연결하지 못함 (A02)
- 직위 "프로"를 직위로 인식하지 못하고 담당 업무를 답함 (A17)
- 전체 mAP50(0.869) 대신 특정 결함 유형의 값(0.995)을 답함 (A09, RAG)

같은 근거로 Gemini는 18문항을 모두 맞혔습니다. 이번 문서에서는 **모델의 문맥 이해력이 성능을 가장 크게 좌우**했습니다.

**2. 재검색(Agent)은 이번 조건에서 정답률을 올리지 못했다**
재검색은 검색 실패를 고치는 기법인데, 이번 실험은 검색 실패가 없었습니다.
- qwen: 26문항에서 재검색 50회(최대 52회). 근거가 충분한 질문에도 거의 항상 "부족하다"고 판단해, 응답 시간만 4.5배, 입력 토큰은 4.1배로 늘었습니다.
- Gemini: 재검색 18회. 문서에 답이 없는 8문항에서 주로 일어나, 채점 판단 자체는 합리적이었습니다. 다만 RAG만으로 이미 100%라 토큰만 2.7배 썼습니다.

→ **작은 모델은 '검색 결과가 충분한지'를 판단하는 채점자 역할을 제대로 하지 못했습니다.** 재검색 구조를 쓰려면 채점 단계에 더 큰 모델을 쓰거나, 검색 실패가 실제로 많은 상황인지 먼저 확인해야 합니다.

**3. 모든 조합이 문서에 없는 내용을 지어내지 않았다**
답변 불가 질문 8개에 네 조합 모두 "모른다"고 답했습니다.

### 평가 과정에서 고친 문제

- **Agent 재검색 판정 버그 (원래 코드):** `"sufficient" in 답변`으로 판정했는데 "insufficient" 안에도 "sufficient"가 들어 있어, 모델이 "부족하다"고 해도 항상 "충분하다"로 처리됐습니다. 수정 전 qwen Agent 실험에서 재검색은 0회였고, 당시 정답률 89%는 재검색이 아니라 프롬프트 차이에서 나온 결과였습니다. 수정 후 다시 측정했습니다.
- **모델별 응답 형식 차이:** Gemini 3 계열은 답을 문자열이 아닌 목록으로 돌려줘 Agent에서 에러가 났습니다. 어떤 모델이든 문자열로 바꾸도록 수정했습니다.
- **채점 규칙 보정 (2회):** 키워드 기반 거절 판정이 "정보는 없음", "모릅니다" 같은 표현을 놓쳐 올바른 거절을 환각으로 집계했습니다. 실패 사례를 직접 읽어 확인하고 규칙을 고친 뒤, 저장된 답변으로 다시 채점했습니다(`rescore.py`).

### 한계
- 질문 수가 적어 1문항이 약 6%p(답변 가능) / 12.5%p(답변 불가)에 해당합니다.
- 문서가 짧아 검색이 쉬운 조건이었습니다. 재검색의 효과는 더 긴 문서에서 다시 측정해야 합니다.
- Gemini 3.5 Flash Lite는 temperature 설정을 무시해 실행마다 결과가 달라질 수 있으며, 이번 결과는 1회 실행 값입니다.
- 키워드 채점은 표현 변형에 약합니다. 다음 단계로 LLM을 채점자로 쓰는 방식과 비교해 볼 계획입니다.
